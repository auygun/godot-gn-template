# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A first-person shooter prototype for Godot 4 (4.7+), written in C++ as a
GDExtension (`src/`) and built with GN + Ninja for Linux, Windows and
Android. It is built on a template that lives on `main` (the build system
plus a bare-bones demo of this game). Game features belong on the game's
branches, never on `main`. Only build and tooling fixes or clear bugs in the
demo go back to the template. `README.md` describes the template, so its
"replace the example game" advice doesn't apply here.

## Commands

```bash
git submodule update --init --recursive
godot --headless --recovery-mode --path . --import   # writes .godot/extension_list.cfg
gn gen out/host                       # release; --args='is_debug=true' for debug
ninja -C out/host                     # builds godot-cpp + libextension.so
ninja -C out/host smoke_test          # the only test: offline + loopback runs
godot --path .                        # play offline (-e for the editor)
godot --path . -- --host [port]       # listen server (default port 24680)
godot --path . -- --join <addr> [port]
godot --headless --path . -- --server [port]   # dedicated server
# ... --lag <ms> --loss <percent> after the mode simulates a bad network

# Android, one ABI per out dir (target_cpu: arm64, x64, arm, x86)
gn gen --args='ndk="/path/to/ndk" target_os="android" target_cpu="arm64"' out/android/release
ninja -C out/android/release          # .so + app.apk (no_apk=true for just the .so)
```

- There are no unit tests. `smoke_test` (`build/smoke_test.py`) runs the main
  scene headless offline, then a dedicated server and a client over
  loopback, and fails on any `ERROR:` line or non-zero exit (or if the
  client never spawns). It is never up to date, so it always runs. CI
  (`.github/workflows/ci.yml`) does the import, a Linux release build and
  `smoke_test`.
- If `.godot/` is missing (e.g. after `git clean -fdx`), or a `.gdextension`
  file was added or renamed, run the import again. Without
  `extension_list.cfg` the game starts with no C++ classes and the scenes
  fail to load.
- The engine binary is `godot` on `PATH`, or `--args='engine_binary="..."'`.
  godot-cpp's bindings are generated from that engine's API dump at `gn gen`
  time. After switching engine versions, delete the out dir.
- Formatting: `clang-format` with the Chromium style (`.clang-format`). The
  game code builds with `-Werror` / `/WX` (`treat_warnings_as_errors`) and
  without exceptions.

## Adding code and assets

- New `.cc` files go into `sources` of `shared_library("extension")` in
  `BUILD.gn`. New classes must also be registered in
  `src/register_types.cc` (`GDREGISTER_RUNTIME_CLASS`), or the scenes that
  use them by type name won't load.
- New scenes and assets (and their `.import` files) go into the `apk`
  action's `inputs` in `BUILD.gn`, or Android builds won't re-export when
  they change.
- Assets in `textures/` and `sounds/` are generated by the deterministic
  scripts in `tools/` (usage is in each script's header). Edit the script,
  not the output.

## Build system layout

- `.gn` → `build/BUILDCONFIG.gn`: gn args (`is_debug`, `ndk`, `ndk_api`,
  `engine_binary`, `no_apk`, `treat_warnings_as_errors`, `is_clang`), platform
  detection, NDK toolchain selection, ccache auto-detection.
- `build/BUILD.gn`: compiler flags as the `default`, `debug`, `release` and
  `warnings` configs. Its defines mirror godot-cpp's cmake files. GN defines
  don't propagate through deps, so they are applied to every target.
- `third_party/godot-cpp/BUILD.gn` + `godot_cpp.py`: generates the bindings
  into `$root_gen_dir/godot_cpp` and builds godot-cpp as a static library.
  The submodule itself is untouched.
- `gdextension/extension.gdextension` maps each platform to its library
  path (`out/host/`, `out/android/{debug,release}/`). The out dir names and
  `output_name = "extension"` must match it.
- Desktop debug builds hot-reload: the editor reloads the rebuilt library
  when its window regains focus. That's why debug builds link libstdc++
  dynamically and use `-fno-gnu-unique` with GCC.
- `build/godot_export_apk.py` exports the APK headless using the preset for
  `target_cpu` and verifies the result, because the export can "succeed"
  with an empty pck. `build/android_debug.py` backs the VSCode "Android
  (lldb)" launch config.

## Game code conventions (`src/`)

- Everything is in `namespace godot`, includes are relative to the repo root
  (`#include "src/weapon.h"`), and naming follows Chromium style
  (`CamelCase()` methods, `member_` fields, `kConstant`). Godot virtuals keep
  their names (`_ready`, `_physics_process`), and methods bound in
  `_bind_methods` get snake_case names for the engine.
- Scenes (`scenes/*.tscn`) instantiate the C++ classes by type name.
  Node wiring happens in C++ `_ready()` through `get_node_or_null` by path
  and `connect` with `callable_mp`. `Main` spawns the players
  (`player_scene`, at the level's `SpawnPoints`) and connects their weapons
  to the `Hud`.
- `FpsCharacter` separates simulation from presentation. Each physics tick,
  `GatherInput()` builds a `PlayerInput` command from the local devices, and
  `Simulate(command, dt)` advances all game state from that command alone
  (movement, aim, recoil, `Weapon::Tick`). Buttons are held states, and
  presses are detected against the previous command. Shots come from
  `AimTransform()` (game state), not the camera. Camera and weapon motion
  (bob, sway, landing dip, look) is local state updated every frame in
  `_process`, drawn between ticks with physics interpolation, which is
  enabled in `project.godot`. Keep new gameplay state on the simulation side
  so a server without devices or a camera could run it.

## Multiplayer (`src/main.cc`, `src/client_prediction.cc`, `src/snapshot_interpolator.cc`, `src/lag_compensation.cc`, `src/net_protocol.h`)

- Server-authoritative. The mode comes from the user args after `--`
  (`Main::ParseCommandLine`); offline is a server without the network, so
  single player runs the server's code. ENet through the SceneTree's
  `SceneMultiplayer`, with our own binary messages (`send_bytes`,
  `peer_packet`), not RPCs or `MultiplayerSynchronizer`. Bump
  `kProtocolVersion` when a message changes.
- `Main::_physics_process` runs each tick before the players' own. The
  server calls `Simulate` for every player, with the local player's
  `GatherInput()` or the client's queued commands (repeating the last when
  none arrived). Every `kSnapshotInterval` (2) ticks it sends each client
  a snapshot: every player's
  `PlayerState` (`src/player_state.h`, everything `Simulate` reads or
  writes), the targets, and the client's last simulated command (`ack`).
  Hits and kills go to the shooter as reliable events.
- A client predicts its own player (`ClientPrediction`): each tick it
  simulates its new command right away (`SimulationMode::kPredicted`:
  effects, but hits and damage stay the server's) and sends its last 4
  commands. On a snapshot, if the server's state after the acknowledged
  command differs from the prediction, it restores the server's state and
  replays the unacknowledged commands (`kReplay`: game state only); the
  camera eases across the difference (`SmoothCorrection`). Prediction uses
  the newest snapshot.
- Everything else a client shows (other players, targets, joins and
  leaves) is drawn ~100 ms in the past by `SnapshotInterpolator`: a render
  clock in server ticks, kept 6 ticks behind the server's estimated time,
  blends the snapshots around it (positions and look; the rest, like
  deaths and respawns, from the older one). Other players get that state
  through `FpsCharacter::ApplyState`, which plays a shot's effects when
  `shot_count` goes up.
- Lag compensation: each command carries the server tick the client was
  drawing (`PlayerInput::view_tick`, the render clock), and the server
  tests that command's shots against the players and targets as they were
  then (at most `kMaxRewindTicks` back). Moved bodies don't show in
  physics queries until the next physics step, so `LagCompensation` keeps
  each tick's hitboxes (from the bodies' `CollisionShape3D`: capsules and
  boxes) and tests rays against them in plain math. `Main` is the
  weapons' `ShotResolver`: the physics ray finds the level (passing
  through the bodies), the history the bodies, and the nearer wins.
- The server simulates each client's commands by sequence number, one per
  tick; a missing one is replaced by repeating the last, and dropped if it
  comes later. Snapshots report how early the client's commands arrive
  (`input_buffer`), and the client keeps that at 2 ticks by skipping
  sequence numbers (late) or a tick's command (too early). Only
  `Simulate`'s inputs and `PlayerState` may affect the outcome, or
  predictions won't match: e.g. floor snapping goes by `on_floor_`, not
  the body's last `move_and_slide`.
- Characters that aren't the local player's (`set_local(false)`) drop their
  camera and touch controls, and their weapon stays on the body. Anything
  new in `Simulate` belongs in `PlayerState` and the snapshot.
- Physics layer 4 `player`: players don't collide with each other, shots
  hit them.
- Deathmatch: a player has 100 health (`PlayerState::health`, `dead`, set
  only by the server: `FpsCharacter::TakeDamage` from `Weapon` hits). A
  dead player's commands do nothing and its body is hidden and off the
  player layer; `Main` counts the kill, and respawns it after
  `kRespawnDelay` at the spawn point farthest from the living. Scores
  (`Main::scores_`) go out in every snapshot. Targets are practice only:
  hit markers, no score.
