# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A first-person shooter prototype for Godot 4 (4.7+), written in C++ as a
GDExtension (`src/`) and built with GN + Ninja for Linux, Windows and
Android. It is built on a template that lives on `main` (the build system
plus a bare-bones demo of this game). Game features belong on the game's
branches, never on `main`. Only build and tooling fixes or clear bugs in the
demo go back to the template. `README.md` describes the template, so its
"replace the example game" advice doesn't apply here.

## Commands

```bash
git submodule update --init --recursive
godot --headless --recovery-mode --path . --import   # writes .godot/extension_list.cfg
gn gen out/host                       # release; --args='is_debug=true' for debug
ninja -C out/host                     # builds godot-cpp + libextension.so
ninja -C out/host smoke_test          # the only test: offline + loopback runs
godot --path .                        # play offline (-e for the editor)
godot --path . -- --host [port]       # listen server (default port 24680)
godot --path . -- --join <addr> [port]
godot --headless --path . -- --server [port]   # dedicated server
# ... --lag <ms> --loss <percent> after the mode simulates a bad network,
# --netstats prints the traffic (kbit/s after compression) every 5 s

# Android, one ABI per out dir (target_cpu: arm64, x64, arm, x86)
gn gen --args='ndk="/path/to/ndk" target_os="android" target_cpu="arm64"' out/android/release
ninja -C out/android/release          # .so + app.apk (no_apk=true for just the .so)
```

- There are no unit tests. `smoke_test` (`build/smoke_test.py`) runs the main
  scene headless offline, then a dedicated server and a client over
  loopback, and fails on any `ERROR:` line, a non-zero exit, or a client
  that never spawns. CI (`.github/workflows/ci.yml`) does the import, a
  Linux release build and `smoke_test`.
- If `.godot/` is missing (e.g. after `git clean -fdx`), or a `.gdextension`
  file was added or renamed, run the import again. Without
  `extension_list.cfg` the game starts with no C++ classes and the scenes
  fail to load.
- The engine binary is `godot` on `PATH`, or `--args='engine_binary="..."'`.
  godot-cpp's bindings are generated from that engine's API dump at `gn gen`
  time. After switching engine versions, delete the out dir.
- Formatting: `clang-format` with the Chromium style (`.clang-format`). The
  game code builds with `-Werror` / `/WX` (`treat_warnings_as_errors`) and
  without exceptions.

## Adding code and assets

- New `.cc` files go into `sources` of `shared_library("extension")` in
  `BUILD.gn`. New classes must also be registered in
  `src/register_types.cc` (`GDREGISTER_RUNTIME_CLASS`), or the scenes that
  use them by type name won't load.
- New scenes and assets (and their `.import` files) go into the `apk`
  action's `inputs` in `BUILD.gn`, or Android builds won't re-export when
  they change.
- `textures/`, `sounds/`, `models/` and `scenes/levels/test_level.tscn` are
  generated by the deterministic scripts in `tools/` (usage is in each
  script's header). Edit the script, not the output. The models come from
  `tools/gen_view_models.py`, a Blender (5.2) script; their `.import` files
  are set by hand (60 fps, all tracks kept, textures embedded). No
  animation loops in the import (a per-animation setting makes Godot write
  ~2000 lines of defaults): `ViewModel` restarts idle itself.

## Build system

- `build/BUILDCONFIG.gn` holds the gn args, platform detection, NDK
  toolchain selection and ccache detection; `build/BUILD.gn` the compiler
  flags. GN defines don't propagate through deps, so they are applied to
  every target.
- `third_party/godot-cpp/BUILD.gn` + `godot_cpp.py` generate the bindings
  and build godot-cpp as a static library. The submodule itself is
  untouched.
- `gdextension/extension.gdextension` maps each platform to its library
  path (`out/host/`, `out/android/{debug,release}/`). The out dir names and
  `output_name = "extension"` must match it.
- Desktop debug builds hot-reload when the editor regains focus. That's why
  debug builds link libstdc++ dynamically and use `-fno-gnu-unique` with
  GCC.
- `build/godot_export_apk.py` verifies the exported APK, because the export
  can "succeed" with an empty pck.

## Game code conventions (`src/`)

- Everything is in `namespace godot`, includes are relative to the repo root
  (`#include "src/weapon.h"`), and naming follows Chromium style
  (`CamelCase()` methods, `member_` fields, `kConstant`). Godot virtuals keep
  their names (`_ready`, `_physics_process`), and methods bound in
  `_bind_methods` get snake_case names for the engine.
- Scenes (`scenes/*.tscn`) instantiate the C++ classes by type name. Node
  wiring happens in C++ `_ready()` through `get_node_or_null` by path and
  `connect` with `callable_mp`.
- Simulation is separate from presentation. Each physics tick,
  `GatherInput()` builds a `PlayerInput` command from the local devices and
  `Simulate(command, context)` advances all game state from it alone.
  Buttons are held states; presses are detected against the previous
  command. Shots come from `GetAimTransform()` (game state), not the
  camera. Camera and weapon motion (bob, sway, look) is local state updated
  in `_process`.
- The camera and the first-person weapon are top-level with physics
  interpolation off, placed every frame from `GetCameraTransform()`, so look
  input shows without a tick of delay. Code that needs the view (e.g.
  during a tick) calls `GetCameraTransform()` rather than reading the
  camera node.

## Multiplayer: the netcode framework (`src/net/`)

- `src/net/` (namespace `godot::net`, its own `source_set("net")`) is
  game-agnostic and must not include anything from the game: check with
  `grep -rn '#include "src/' src/net/ | grep -v '"src/net/'`.
- Server-authoritative; offline is a server without the network, so single
  player runs the server's code. ENet through `SceneMultiplayer` with our
  own binary messages (`send_bytes`, `peer_packet`), not Godot's RPCs or
  `MultiplayerSynchronizer`.
- Every replicated struct (entity states, the command, RPC payloads) lists
  its fields once in `template <class V> void Replicate(V& v)`:
  `v(field, codec, flags[, draw, ease, snap])`. Encoding, deltas,
  quantization, reconciliation, blending and drawing are all generated from
  it; the codecs, flags (`kOwner`/`kOthers`/`kAll`, `kPredicted`, `kServer`,
  `kBlend`, `kTeleport`, `kAngular`) and draw/ease functions are documented
  in `replicate.h`. Structs must be trivially copyable and at most
  `kMaxStateSize`.
- `Main::_ready` registers the `Schema` (command, entity types, RPCs) in the
  same order on every side. Clients send its hash on connecting and a
  mismatch is rejected, so there is no protocol version to bump;
  `kWireVersion` only covers the framework's own format.
- Entity types: `AddEntityType<Class, State>(scene, parent_path)` for a C++
  entity (the scene's root derives from `net::TypedEntity<State, Command>`),
  `AddNodeType(scene, parent_path)` for any `Node3D` scene without game code
  (`NodeEntity` replicates its transform). The server calls
  `NetSession::Spawn` / `Despawn`, and clients follow the snapshots. A peer
  owns at most one entity: the one its client predicts. Entities placed in
  the scene are matched by tree order, so every side must load the same
  scene. Nodes of unregistered types are local to each machine.
- A client predicts its own entity and replays unacknowledged commands when
  the server's state differs; everything else is drawn ~100 ms in the past.
  `SimulationMode` tells `Simulate` which: `kAuthoritative` (server: hits
  and damage), `kPredicted` (client: effects only), `kReplay` (nothing).
- Only `Simulate`'s inputs and the state struct may affect the outcome, or
  predictions won't match: e.g. floor snapping goes by `on_floor`, not the
  body's last `move_and_slide`, and a physics query must start from game
  state such as `GetAimTransform()`. `FpsCharacter` and `Weapon` simulate on
  their state struct (`state_`), so anything new in `Simulate` is just a
  field of `PlayerState` (or `WeaponState`) with a `Replicate` entry.
- Lag compensation: each command carries the tick its client was drawing
  (`SimContext::view_tick`); the game does the rest. `Main` records the
  hitboxes of entities in the `lag_compensated` group (capsules and boxes
  from their `CollisionShape3D`) and resolves shots against that history. A
  body is hittable while it is on a layer in `Weapon::kShotMask` with its
  shape enabled.
